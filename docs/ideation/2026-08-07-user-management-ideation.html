Grounding Context

SkillHub 是一个轻量级、自托管的 Hermes Agent 技能注册中心。技术栈：FastAPI + SQLite (aiosqlite) + Click CLI + 原生 JS Web UI。

关键历史背景：项目此前曾有基于 API Token 的认证系统，但因 SHA-256 哈希比对 bug（原始 token 与存储的哈希直接比较导致所有认证请求返回 401）被完整移除。移除计划记录在 docs/plans/2026-07-20-001-feat-remove-auth-plan.md。当前所有 API 端点完全公开，无任何访问控制。

当前状态：

  • skills 表有 published_by 字段但始终为 None
  • Web UI 的删除按钮无任何保护，任何人可删除任何技能
  • CLI skillhub push 无认证要求
  • 无用户表、无会话管理、无密码存储
  • Docker 部署使用非 root 用户运行

项目约定：

  • 配置通过 ~/.skillhub/config.yaml + 环境变量
  • 数据库使用 aiosqlite，异步操作
  • 前端为原生 JS，无框架依赖
  • 支持中英文双语 (i18n)
  • pyproject.toml 使用 hatchling 构建

相关解决方案文档：

  • docs/solutions/runtime-errors/auth-token-hash-mismatch.md — 之前认证 bug 的根因分析
  • docs/solutions/architecture-patterns/adding-crud-delete-to-web-frontend.md — 前端 CRUD 模式参考

1. JWT + bcrypt 认证系统

认证机制

构建基于 JWT (JSON Web Token) 的无状态认证系统，使用 bcrypt 进行密码哈希存储。用户注册时密码经 bcrypt 加盐哈希后存入 users 表；登录时验证密码并签发 JWT；后续请求通过 Authorization: Bearer <token> 头携带凭证。JWT 的无状态特性避免了服务端会话存储的复杂度，适合 SQLite 的单文件部署场景。

JWT 认证流程：登录签发 token，后续请求无状态验证

基础依据：direct: 之前的认证系统因 SHA-256 哈希比对 bug 被移除 (auth-token-hash-mismatch.md)；bcrypt 是经过验证的密码哈希方案，从根本上避免了自定义哈希逻辑的错误风险。
为何重要：这是整个用户管理系统的基石。没有认证，后续的授权、所有权、审计都无从谈起。JWT 的无状态特性与 SkillHub 的轻量定位高度契合。
置信度：High
复杂度：Medium

2. 基于角色的访问控制 (RBAC)

授权与权限

定义三种角色：admin（管理员，可管理用户和所有技能）、publisher（发布者，可发布和管理自己的技能）、viewer（观察者，只读访问）。每个 API 端点通过 JWT 中的角色声明进行权限检查。admin 角色默认分配给首个注册用户（自托管场景的常见模式）。

基础依据：reasoned: 一个允许多用户发布的注册中心必须区分权限级别——否则任何注册用户都能删除他人技能。npm、PyPI 等包注册中心均采用类似的 ownership + maintainer 模型。
为何重要：权限控制是多用户系统的核心安全机制。没有 RBAC，"用户管理"只是增加了登录步骤，没有真正保护资源。
置信度：High
复杂度：Medium

3. Web UI 登录/注册页面

集成层面

在现有 Web UI 中添加登录和注册页面。注册表单包含用户名、邮箱、密码字段；登录表单包含用户名和密码。登录成功后将 JWT 存储在 localStorage，后续 API 请求自动附带 Authorization 头。未登录用户只能浏览技能列表（只读），登录后显示发布和删除按钮。保持现有的 i18n 双语支持。

基础依据：direct: 现有 Web UI (skillhub/static/js/app.js) 无任何认证交互；删除按钮直接暴露给所有访客。前端 CRUD 模式文档 (adding-crud-delete-to-web-frontend.md) 提供了添加新 UI 功能的六步清单参考。
为何重要：Web UI 是最常见的交互入口。没有登录页面，用户无法通过浏览器完成认证，JWT 系统对 Web 用户不可用。
置信度：High
复杂度：Medium

4. CLI 认证命令

集成层面

添加 skillhub auth login、skillhub auth logout、skillhub auth status 三个 CLI 命令。login 命令交互式输入用户名密码，获取 JWT 后存储到 ~/.skillhub/config.yaml 的 api_token 字段。push 命令自动从配置读取 token 并附带 Authorization 头。logout 清除存储的 token。

基础依据：direct: 之前有 skillhub auth 命令组 (在移除计划 U6 中记录)，但因认证系统整体被删除而移除。现在需要以 JWT 方式重新实现，修复之前的 token 存储和验证流程。
为何重要：CLI 是开发者发布技能的主要工具。skillhub push 无认证意味着任何人都能向注册中心推送技能，这在多用户场景下不可接受。
置信度：High
复杂度：Low

5. 技能所有权追踪

安全基础

将 skills 表的 published_by 字段从始终为 None 改为存储发布者的 user_id。发布技能时自动关联当前认证用户；Web UI 显示每个技能的发布者；拥有者可以编辑和删除自己的技能；admin 可以管理所有技能。这利用了已有的数据库字段，改动最小但效果显著。

基础依据：direct: skills 表已有 published_by TEXT 字段 (database.py:23)，SkillResponse 模型已有 published_by: Optional[str] (models.py:25)，但从未被赋值。基础设施已就绪，只需接入用户系统。
为何重要：所有权是授权的前提——没有"谁发布的"就无法实现"只能删除自己的"。这个改动是连接用户系统和技能数据的桥梁。
置信度：High
复杂度：Low

6. API Key 管理

认证机制

除 JWT 会话令牌外，支持创建和管理长期有效的 API Key。用户通过 Web UI 或 CLI 生成 API Key（类似 GitHub Personal Access Tokens），用于 CI/CD 管道和自动化脚本。API Key 存储为 bcrypt 哈希（吸取上次的教训），支持设置过期时间和权限范围（只读/读写）。CLI 的 skillhub push 可通过 --token 参数或环境变量 SKILLHUB_TOKEN 传入。

基础依据：external: npm (npm token create)、PyPI (API tokens)、GitHub (Personal Access Tokens) 均提供 API Key 机制用于自动化场景。JWT 适合交互式会话，API Key 适合程序化访问——两者互补。
为何重要：开发者需要在 CI/CD 管道中自动发布技能，JWT 的短有效期不适合此场景。API Key 解决了"如何在脚本中认证"的问题。
置信度：Medium-High
复杂度：Medium

7. 邀请码注册机制

用户生命周期

为自托管场景提供可选的邀请码注册机制。管理员在配置中启用 require_invite_code: true，新用户注册时需要输入有效的邀请码。邀请码由 admin 通过 CLI (skillhub admin invite-code generate) 或 Web UI 生成，可设置使用次数限制和过期时间。未启用时任何人可自由注册。这平衡了开放性和可控性。

基础依据：reasoned: 自托管注册中心的典型场景是团队或组织内部使用，不希望外部人员随意注册发布技能。邀请码是最低摩擦的访问控制方式——不需要邮件服务，不需要 SSO，只需一个字符串。Discourse、Mastodon 等自托管平台广泛采用此模式。
为何重要：没有注册控制的用户管理系统是不完整的——任何人都能注册意味着访问控制形同虚设。邀请码以极低的实现成本解决了这个问题。
置信度：Medium
复杂度：Low

1魔法链接 / 无密码认证需要邮件基础设施，与"轻量自托管"定位冲突
2OAuth / SSO 集成 (GitHub, Google)引入外部依赖，增加部署复杂度，超出轻量级范围
3用户个人主页 / Dashboard锦上添花，非核心用户管理功能；可作为后续迭代
4每用户速率限制重要但属于运维层面，应在核心用户管理之后实现
5审计日志（谁发布了什么）依赖用户系统和所有权追踪，是后续增强而非核心
6团队 / 组织支持范围过大，当前阶段单用户角色模型足够；可后续扩展
7OAuth Provider 自建（如 Keycloak）过度工程化，与 SQLite + 单文件部署的轻量架构不匹配
82FA / TOTP 双因素认证自托管场景下优先级低，增加用户摩擦；可作为未来增强
9密码重置邮件流程需要邮件服务；自托管场景下管理员可直接重置数据库
10社交登录 (微信、钉钉)中国开发者场景有吸引力但引入外部 API 依赖，与自托管矛盾
11OAuth 回调安全 (CSRF, PKCE)依赖 OAuth Provider，当前无此需求
